## Что это за система
- **NVGRN Hub** — ERP: Node.js + Express + EJS + PostgreSQL, деплой на Railway
  (`nvgrnerp-production.up.railway.app`). Точка входа — `server.js` (в корне), который
  подключает модули из `src/`. Корневые дубликаты `db.js`/`server.js` (если есть) — легаси, не трогать.
- **Telegram-бот** — отдельный сервис в подпапке `tg-bot/` (свой `package.json`, `index.js`,
  `db.js`, `schema.sql`). Заказы/напоминания для HoReCa. **Бот и Hub живут в одном репозитории
  и в одной базе PostgreSQL.**
- **SalesDoctor (SD)** — внешняя CRM, источник данных по клиентам/агентам/заказам.

## Деплой и git
- Railway деплоит **автоматически при пуше** в репозиторий.
- **Schema-first:** если добавляются колонки/таблицы в БД — сначала деплой Hub (он создаёт схему),
  потом бот. Hub впереди бота.
- После деплоя пользователь делает Ctrl+Shift+R (сброс кэша).
- **Перед каждым пушем обязательно:** `npm run verify` (синтаксис всех JS + компиляция всех EJS
  + охранные правила + тесты). Красный результат = не пушим. То же гоняет CI на GitHub.
- Работаем в общем репозитории **несколько человек**. Поэтому: **перед началом работы
  `git pull`**, перед пушем — ещё раз. Не «чинить» чужой свежий код, не поняв замысла.

## Правила изменений (несколько разработчиков)

**Инварианты — ломать нельзя без решения Шоха.** Это фундамент, на нём стоят цифры:
1. **Единый реестр движений = источник правды.** Остаток склада = сумма `stock_movements`.
   Остаток денег = сумма транзакций Кассы. Никаких параллельных «итоговых» колонок,
   которые считаются отдельно и могут разойтись с реестром.
2. **Стартовые миграции не удаляют данные.** Только `CREATE TABLE IF NOT EXISTS` /
   `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`. Никогда `DROP TABLE`/`TRUNCATE` при старте
   приложения (проверяется автоматически в `npm run check`).
3. **Долг поставщику считается в одном месте** — `src/purchase-finance.js`. Закуп и
   Касса→Обязательства обязаны брать цифру оттуда, а не считать свою.
4. **Доступ по плитке роли** (`requireXAccess`), файлы через `/file/:id` — только с проверкой
   прав. Секреты (JWT, токены) — только из переменных окружения, не в коде.
5. **Справочники в БД, не в коде.**
6. **Переводы между своими счетами — не доход и не расход.** Классифицируем на входе.

**Что НЕ оцифровываем (осознанно).** Не всё стоит загонять в систему: часть вопросов
решается административно, и попытка «подогнать под цифру» создаёт бардак и мёртвые поля.
- Разовое и договорное (уступки, индивидуальные условия, «по-человечески договорились») —
  фиксируем **комментарием/файлом**, а не новым полем или отдельным модулем.
- Не автоматизируем то, что **не повторяется** (реже раза в месяц), **не измеряется**
  или **ни на что не влияет** в деньгах/сроках/качестве.
- Система **записывает факт**, а не командует людьми. Не строим «согласования по цепочке»
  и обязательные статусы там, где вопрос решается разговором.
- Не заводим новых сущностей/справочников/статусов ради красоты отчёта.
  Сначала — можно ли решить существующим полем или комментарием?
- Не плодим отчёты «на всякий случай». Отчёт делается под конкретное решение,
  которое кто-то реально принимает.

**Порядок работы над новым:**
- **Новая плитка/модуль, новая таблица в БД, новое обязательное поле в существующей форме,
  изменение формулы денег** — только после явного «да» от Шоха (он владелец процессов).
  Сначала одним абзацем: какую задачу решаем, кто этим будет пользоваться, что будет,
  если не делать. Если ответа нет — не строим.
- **Мелкие правки** (тексты, вёрстка, читаемость кнопок, сортировка, багфиксы) — свободно.
- Каждый шаг — **отдельный протестированный коммит** с понятным сообщением по-русски.
- Если задача выглядит как «давайте всё оцифруем» — сначала спросить Шоха, не решается ли
  это административно. Честно сказать о риске мёртвого функционала.

## КРИТИЧНО: безопасность бота
- Файлы бота — в `tg-bot/` (`index.js`, `db.js`, `schema.sql`) плюs его обвязка.
  Раньше частичные заливки роняли прод. С git это снято, но всё равно:
  **менять бота отдельными, отдельно протестированными коммитами.**
- Hub-сторона бота (плитка «Бот HoReCa») — это `src/tgbot.js`. Это НЕ сам бот.
  Hub читает/пишет схему бота напрямую через префикс `tgbot.` (та же база).

## Архитектурные принципы
- **Единый реестр движений = источник правды.** `stock_movements` — единственный
  складской реестр; остаток = сумма движений. Тот же принцип для будущей Кассы.
- **Общие таблицы вместо синхронизации:** бот пишет, Hub читает через `tgbot.<table>`.
- **Справочники в БД, не в коде** — чтобы кнопки бота и выпадашки Hub были в синхроне
  без передеплоя.
- **Внутренние переводы классифицировать на входе**, не отфильтровывать в отчётах.

## Фича «Претензии» (в работе)

Жалобы клиентов: подача из бота → разбор в вебе → дашборд. Две фазы:
клиент даёт факты, внутренние поля (степень/решение) ставит Шох/РОП в вебе.

- `src/complaints-schema.js` — **единый источник** схемы и справочника. Таблицы в схеме `tgbot`:
  - `tgbot.complaint_dicts` — справочник: 19 типов жалоб (каждый с «звеном»
    field/production/packing/fulfillment), 3 степени, 4 решения, 3 категории, 4 звена.
    Сидируется идемпотентно (`ON CONFLICT DO UPDATE`).
  - `tgbot.complaints` — поля разнесены по фазам: клиент / реакция агента / обработка в вебе.
    Статусы: `new → agent_reacted → in_review → resolved`.
  - `tgbot.complaint_files` — медиа (`photo`/`video`/`video_note`), байты в `public.files`,
    отдаются через существующий эндпоинт `/file/:id`.
  - `src/tgbot.js` вызывает `ensureComplaintSchema(db.pool)` — НЕ дублировать сид в нём.
- `src/complaints.js` — модуль `/complaints`: страница + API (`/dicts`, `/list`, `/one/:id`

  (заменяет строки `source='import'`). **Важно:** колонка «Продукт» берётся точно

- `src/views/complaints.ejs`, `public/complaints.js`, `public/complaints.css` — UI.
  Две вкладки: **Дашборд (по умолчанию)** и **Список**. Дашборд — фильтр по месяцу
  (по умолчанию текущий), KPI с Δ месяц-к-месяцу, матрица продукт×месяц (герой),
  пончик по звеньям, тренд, топ типов, таблица агентов. Графики — собственный inline SVG
  (без внешних библиотек). Список — фильтры, карточка с фото/видео, простановка
  степени/решения/статуса, выгрузка Excel, импорт.
- Плитка «Претензии» сидируется в `src/db.js` (url `/complaints`).
- Тип жалобы → «звено» (на чью зону указывает косяк):
  - field (поле/сырьё): живность, грязь, переросший, курчавость, неоднородный калибр, изменение цвета
  - production (производство/сушка): избыточная влажность, завядание, пожелтение, потемнение, запах
  - packing (фасовка): поломанные листья, нарушение вакуума, нет ТМ, лишние стебли
  - fulfillment (комплектация/логистика): неположили, нарушение веса, пересорт, проблема со сроком

## Себестоимость в P&L (методика, решение Шоха, сентябрь 2026)

Считает только `src/cash-pnl.js` — карточка месяца, график и Excel обязаны брать
цифру оттуда, своих формул не заводить.

- **Цена сырья и упаковки** — средняя цена приходов **этого месяца**; нет приходов в
  месяце — последняя известная цена до него (`monthlyPriceMaps`). Накопительная средняя
  «с начала времён» и цены «до конца всего отрезка» запрещены: от них прошлое плывёт.
- **Факт себестоимости** — материалы, выданные в производство за месяц (`factCogs`).
  Осознанно считаем это приближением себестоимости проданного: у свежей зелени
  выдача и отгрузка происходят в одни дни. Отход и списания — отдельными строками.
- **План** — по ассортименту: штуки каждого товара из SD × его зелень и упаковка из
  Калькуляции (`planCogs`, разбивка продаж хранится в `settings.pnl_sku_<период>`).
  Связь товара — `calc_sheet_products.sd_product_id`. Товары без связи в сумму НЕ
  попадают и показываются строкой «не оценено». «Средняя пачка» осталась только для
  месяцев, подтянутых до этой правки, и помечена как грубая оценка.
- **Закрытый месяц** — из снимка (`settings.pnl_snapshot_<период>`), снимок делается при
  закрытии месяца в Кассе, снимается при открытии. Закрытый месяц не пересчитывается.

## Единый интерфейс Hub (правило, проверяется автоматически)

Одинаковые вещи должны выглядеть и работать одинаково во всех плитках — иначе
пользователь на каждом экране заново учится пользоваться системой.

**Выбор периода — только `HubDateRange`** (`public/daterange.js`, вид как в SalesDoctor:
одна кнопка с подписью периода словами, внутри готовые варианты и произвольный отрезок):
```js
HubDateRange.create({
  mode: 'range',            // 'month' — если расчёт помесячный (P&L, Калькуляция)
  from: state.from, to: state.to,
  onChange: (v) => { state.from = v.from; state.to = v.to; reload(); },
})
```
Своих полей «с … по …» больше нет нигде. Компонент сам меняет перепутанные даты
местами — раньше «с 01.09 по 31.08» молча давало нули. Экран обязан подключить
`/static/daterange.css` и `/static/daterange.js`.
Одиночная дата (дата документа, «перейти к дню») — обычное поле, правило её не трогает.

**Вкладки — `public/tabs.css`** (`.hub-tabs` / `.hub-tab`, активной класс `.on`).
Подключается последним, после стилей плитки. Там же два вида второго уровня:
- **раздел внутри вкладки** (Обязательства: Сводка / Поставщики / Кредиты) —
  мелкие вкладки с чертой, `.hub-subtabs` / `.hub-subtab`;
- **переключатель вида** тех же данных (Текущие / Утверждённые, По направлениям /
  По товарам, горизонт 7 / 30 / 90 дней) — сегментный, `.hub-seg` / `.hub-seg-it`.
Не путать с таблетками-фильтрами со счётчиками (см. ниже) — у тех другая роль.

**Строка фильтров — `public/filters.css`** (`.hub-bar`, в Закупе/Складе `.pur-bar`):
все фильтры в один ряд, одной высоты, период первым, **без подписей сверху** —
список говорит о себе первым пунктом («Все поставщики»). Подпись в строке
(`.hub-bar-lab`) — только для параметра-действия без пункта «Все» («Куда передать»,
«Операция»), и ставится после фильтров. Поля формы в окне — `.form-row`, там
подписи над полями уместны. Старый `.pur-filters` запрещён проверкой.

**Срезы списка — таблетки со счётчиками** (`public/chips.js`, `HubChips.create`)
вместо выпадающего списка «Все статусы»: количества видно сразу. Считать их
на сервере надо БЕЗ фильтра по самому статусу, иначе соседние цифры обнулятся.

**Шапка плитки — одна на весь Hub**, `src/views/partials/topbar.ejs`:
```ejs
<%- include('partials/topbar', { title: '🛒 Закуп' }) %>
```
Слева кнопка возврата, логотип и название; справа индикаторы связей, колокольчик
и имя. Для подстраницы — `backHref` и `backText`. Своих `<header class="topbar">`
в плитках больше нет (исключение — лаунчер: там меню пользователя).

Все эти правила проверяет `npm run verify`: попытка снова завести свою пару дат или
забыть подключить компонент останавливает пуш.

## Тон и порядок работы
- Каждый шаг — отдельный протестированный коммит, с обкаткой между этапами. Без over-engineering.
- Сначала читать актуальные файлы репозитория, потом предлагать решение (не строить на догадках).
- Отвечать кратко, по-русски, по-человечески.
